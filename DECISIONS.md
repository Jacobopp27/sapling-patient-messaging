# Decisions and tradeoffs

| # | Decision | Why | Tradeoff |
|---|---|---|---|
| 1 | **The LLM interprets; code decides and speaks.** The interpreter returns a structured `Interpretation`, and handlers in code act and reply from templates. | Safety is pass/fail. A prompt lowers risk; code removes it. Behaviour is also deterministic and testable line by line. | Replies are less fluid than model-written text. |
| 2 | **Emergency guard runs first, in code, in every mode.** The exact text is a constant, and nothing is appended to it. | Step 11 must be word for word, and it can't depend on a network call. Claude can *add* an emergency flag, but it can't clear one. | Keyword detection over-triggers by design. A false positive costs one unnecessary 911 message. |
| 3 | **Reply guard on every outgoing message.** It blocks booking claims, time promises and dosing language, then falls back to a safe handoff. | Defence in depth: it protects against a careless template edit or a future model-written reply. | Regexes can be too strict. The tests pin the real templates as allowed. |
| 4 | **No tool to book, cancel, approve or edit the record.** | The agent can't do what it has no capability for, whatever the model says. | None for Phase 1; this is exactly the spec. |
| 5 | **Request catalog** (`server/requests.ts`): required fields and a dedupe key per type. | One place defines "enough for staff to act". It drives the "Ready for staff / Needs follow-up" badge and the dedupe. A new type is one entry. | Required fields are static, not conditional. |
| 6 | **Dedupe by (type, key).** Appointments are keyed by reason and refills by medication. | Step 3 updates request #1 instead of creating #2. A repeat refill ask appends to the open refill. | Assumes one open appointment request per reason. |
| 7 | **The conversation state (`pending`) lives on the outbound message.** | The "yes" in step 1 is matched to what message 0 actually offered, and that survives a restart because it's in SQLite. There's no separate state machine to keep in sync. | Only the latest outbound message's `pending` counts. |
| 8 | **"Thursday instead" resolves against the requested date's week (Nov 12), not tomorrow (Nov 5).** While answering the clinic's offer, a bare "Thursday" also means the Thursday with openings. | "Instead" refers to the Tuesday already chosen. Right after the agent listed "Thursday, Nov 12 (1:30 or 4:00 p.m.)", "the 4pm on Thursday" means that slot; tomorrow has none. | With no offer in play, a bare "Thursday" still means the next Thursday. The date is always said back. |
| 9 | **Reason and provider come from the record.** BP recheck and Dr. Priya Lee come from the clinic's offer and `last_visit`. | Never ask Alex for something we know: zero follow-ups. | If the clinic's message doesn't say what the visit is for, the agent asks once. |
| 10 | **Aetna: offer, don't auto-file.** | Filing unrequested work adds staff load. Step 12 expects only the three things Alex asked for. A "yes" files an `other` request (tested). | Alex has to say yes. |
| 11 | **Emergency handoffs are hidden from Alex's request list.** | The spec says never to tell Alex that staff will review an emergency. | None. Staff still see it at the top of the queue, in red. |
| 12 | **Clinical reply ends with the generic 911 line.** | It's a safety net, not advice: it says nothing about readings, dosing or the medication. | Slight repetition. |
| 13 | **SQLite (better-sqlite3) plus Express rather than Postgres plus NestJS.** | Zero setup for the reviewer. Synchronous queries keep the store trivial. The tables map 1:1 to Postgres. | No migrations framework; the schema is created on boot. |
| 14 | **Scenario clock as a setting that keeps running.** "Now" is the configured time plus the real time elapsed since it was set, and it survives restarts. Reset restarts it. | The spec asks for a configurable "now". A frozen clock gave every row the same `created_at` and `updated_at`, so an inspected record hid the step-3 update. | A demo left running long enough moves past the scripted time; Reset puts it back. Tests fake the machine clock where timing matters. |
| 15 | **Claude interpreter uses structured JSON output with low effort and falls back to rules on any error.** | It can't return an unknown intent, and an outage degrades to local mode instead of failing the message. | Adds latency per message in Claude mode. |
| 16 | **A booked appointment and a pending request are different records.** "Move" or "cancel my physical" files an `appointment_change` request and never edits the recheck. If "my appointment" could mean either, the agent asks which. | The script separates them in step 5. The obvious next question is what happens when Alex wants to change the one that *is* booked. Before this, "move my physical" edited the recheck request, and "cancel my physical" only quoted the FAQ while filing nothing. | One more request type. The agent still can't move or cancel anything; it asks staff. |
| 17 | **Closed days are checked before a request is filed.** Federal holidays are computed (5 U.S.C. 6103, with Saturday/Sunday observance), and weekends come from the FAQ hours. | The FAQ says "closed weekends and federal holidays". The scenario's "next Wednesday" is Nov 11, Veterans Day. Filing it would create a staff follow-up the agent could have avoided. | Clinic-specific closures (staff training days, the day after Thanksgiving) aren't in the data, so they aren't known. |
| 18 | **The agent reads requests in every status, not only open ones.** | After staff mark the recheck completed, "is it booked yet?" used to answer "you don't have a request", which was misleading and invited a duplicate. Now it reports "completed" without claiming a booking, or "closed" with an offer to request again. | The record's booked appointments don't change when staff complete a request, so the agent can't say what was booked. |
| 19 | **Declining the clinic's outreach is logged for staff** (`outreach_declined`). It isn't listed back to Alex as something they asked for. | Dr. Lee asked for the recheck. Without a note, staff can't tell "no reply" from "said no" and would reach out again. | One more card in the queue. |
| 20 | **Every message stores the simulated from/to numbers.** | The spec describes the phone as sender metadata. It belongs in the data model, not only on screen, and it's where identity checks would start. | Phase 1 still treats every inbound message as Alex. |
| 21 | **Second requests in one message are named back, not handled.** The rules read each sentence or "also …" part; Claude returns `also`. | Dropping half a message silently is worse than asking Alex to resend it. | Alex has to send it again. Splitting into separate requests is a next step. |
| 22 | **One sender in the thread; the first automated reply discloses it in the text.** | On a real phone, every message comes from the clinic's number, and an "automated" label in our UI wouldn't exist. Transparency has to live in the SMS itself. | One extra sentence in the first reply. The emergency text stays exact, so a thread that starts with an emergency discloses on the next reply. |
| 23 | **A sweep of interviewer-style messages became a test file** (`tests/variations.test.ts`). | Reviewers won't only replay the script. Running 32 paraphrases found three missed emergencies ("going to pass out", "can't feel my left arm", blurry vision with a severe headache), "did you book it?" being read as a new preference, and record questions ("who is my doctor?") going to staff. All were fixed, and the sweep now guards them. | It's still a keyword interpreter: the sweep shows where it holds, not that it's complete. Spanish and small talk fail safe by offering staff. |
| 24 | **Hosted on Vercel with Neon Postgres, without changing the agent.** Each request runs as one transaction: take an advisory lock, load the thread into a `MemoryStore`, run the agent as usual, write back only what changed, commit. Locally it's still SQLite. | Vercel functions lose their disk, and the spec still requires a local mode with no accounts. Keeping the store's synchronous interface meant no handler had to become async. The lock makes concurrent serverless invocations behave like the local message queue. | Loading the whole thread per request only works because it's one patient and a short thread. A real multi-patient system would query per thread and use database ids instead of max+1. |
| 25 | **The clinic's open offer is remembered across replies.** Besides what the latest outbound message waits for, the agent also looks for the clinic's latest appointment offer that no request has come from yet. | Found in the live demo: one message the agent didn't understand ("thursdar 1:30 works") replaced the pending offer, and every later day choice got "What's the visit for?". That's asking Alex for something the clinic already said, an avoidable follow-up. Weekday typos are now matched too, at an edit distance of 1 (2 for longer words), with the same first letter. | An old, unanswered offer still supplies the reason for a new visit request until a request is filed from it. The reason is always said back, so Alex can correct it. |
| 26 | **Staff close a request with an outcome, and the agent reports it.** Resolve… records booked (date, time, provider), couldn't book, approved, denied, done or replied, plus an internal note. Staff can text Alex an update from an editable draft. | A status alone ("completed") left the agent unable to answer "is it booked yet?", which was a gap a reviewer pointed out. Now the staff record is the source of truth: the agent repeats it with templates ("Clinic staff booked your BP recheck for…"), and booked visits join the upcoming appointments. The agent still has no tool to book or approve, and it never repeats staff's internal notes. | The update text is staff's words and isn't checked by the reply guard, which only covers the agent. There's no automatic notification and no audit log yet. |
| 27 | **"Can't", "doesn't work" and "busy" rule a day or time out instead of choosing it.** A picked open time is the only slot said back and stored. | Found by hand: "I can't at 3:30pm" moved the request *to* 3:30, the opposite of what Alex meant, so staff would have booked the wrong time. Ruled-out times and days are stored for staff (`avoid_times`, `avoid_days`). Ruling out the requested day takes it off the request, so the card says "missing date" instead of a day Alex can't do. | Keyword negation only covers common phrasings. "Anything but 3:30" or a sentence that rules one thing out and picks another needs Claude mode. |
| 28 | **"Change it" / "move it" refers to what was just discussed.** That's the open request if there is one; otherwise the visit staff most recently booked from Alex's request. | Found by hand: after staff booked the recheck, "I need to change it to tuesday" got "What's the visit for?", because the request was closed and "it" named nothing the rules knew. Now it files a change to that booked visit and lists the new day's open times. | A pronoun is a guess. The reply always names the appointment and both dates, so Alex can correct it. |
| 29 | **A change staff carry out replaces the earlier booking; until then the old one stays.** The agent and the console follow the chain of changes for each visit staff booked. "Move it to Thursday" for a visit in the next two weeks means that week's Thursday; a time alone means the same day. | Found by hand: after a move request, the Tuesday booking still read "Booked", and "Thursday" landed on tomorrow, a day with no openings. Keeping the old booking until staff confirm the new one means Alex never ends up with no visit; replacing it afterwards means nobody acts on a stale time. | A change only points at a visit by "type date time", so two visits of the same type at the same time can't be told apart. For a demo with one patient, that's fine. |
| 30 | **One conversation per visitor on the hosted demo.** The browser generates a thread id, keeps it in local storage and sends it on every call. Postgres stores every row under that id (composite keys), and each request locks only its own thread. | Asked by the reviewers: two people opening the live link saw and reset the same conversation. The data stays server-side, so it survives restarts and can be inspected like the rest, and it's still keyed by something only that browser holds. | A thread id isn't authentication: anyone who has the id can open that thread. That's fine for synthetic data in a demo; real patients would need login. Old threads aren't cleaned up yet. |
| 31 | **Questions about open times are answered, never filed.** A new intent, `availability_question` ("any openings Monday?", "is this week available?"), answers from the open slots for that day or week and keeps the clinic's offer pending, so the time Alex then picks becomes the request. | Found in Claude mode by hand: "are openings for Monday?" filed a Monday request staff would have to bounce, and "is this week available?" just repeated "what day works?". Claude Haiku 5.5 classifies these correctly once the intent exists; the rules interpreter got the same patterns. | The answer only knows the supplied open slots. "Is Dr. Lee in on Monday?" can't be answered beyond "no open times". |
| 32 | **Voice calls use OpenAI Realtime only as ears and text-to-speech only as a mouth; the agent in between is the same as for SMS.** Each transcribed sentence goes through `/api/messages` with a call id, and the reply is spoken word for word. The browser gets a 10-minute client secret, never the key. | A speech-to-speech model would choose its own words. Then the emergency text couldn't be guaranteed word for word, and the reply guard couldn't stop it promising a booking. This way every safety rule and test that holds for texts holds for calls, and the call is in the same thread staff see. | Slower than speech-to-speech (about 2–4 s a turn) and less natural: no interruptions mid-word beyond stopping playback, and no tone. Costs per minute of audio, so it's off on Vercel unless `ALLOW_VOICE=true`. |
| 33 | **Claude's structured-output schema has every field required and nullable** (`null` = not said); nulls are dropped before the agent sees the result. | The schema grew to 14 optional fields and the API began answering "Schema is too complex" or timing out while compiling it. Every Claude message fell back to the rules, and only the why panel showed it. Required-plus-nullable is the shape the API compiles quickly (1.5–3 s per message again). Fallbacks are now also logged on the server. | Claude has to write `null` for every field, a few more output tokens per message. A test fails if an optional field is added back. |
| 34 | **The answer to "What's the visit for?" is stored as a short visit name.** Claude returns it in a `reason` field ("BP check"); the rules strip lead-ins ("I need to", "I'd like", "it's for") and call any blood-pressure check "BP check" or "BP recheck", the clinic's own wording. | Found on a voice call: the request read "a I need to check my blood pressure", which staff would have to rewrite. | The rules only know the blood-pressure wording; other reasons keep Alex's words minus the lead-in ("visit to talk about my knee"). |
| 35 | **Track B scores with assertions, not an LLM judge**, and safety is checked independently of the agent's reply guard. Staff touches follow the brief's definition: each missing, wrong, incomplete or extra request is one more message staff would send Alex. | The things that matter (the exact emergency text, a date, a field on a request) are checkable exactly. A judge model would add its own nondeterminism and cost to every run, and could miss what an assertion can't. | Context checks are only as good as the per-case expectations; a reply can be awkward and still pass. |
| 36 | **The before/after change: the emergency guard also recognises Spanish** (same signal groups, matched with accents removed). | The first eval run's only safety failure: local mode answered a Spanish chest-pain message with "pass this to staff?". Claude mode caught it only because the model flagged it. The guard is supposed to be the thing that never depends on the model. | Spanish only; other languages still rely on Claude mode's semantic check. The rest of local mode stays English-only and fails safe. |
